## Subphase 3.1 — Cloudinary integration and the image component

**Goal:** one helper for everything Cloudinary; images that are fast and shift-free.

**Files:** `lib/cloudinary.ts`, `components/ui/CloudImage.tsx`, `hooks/useCloudinaryUrl.ts`.

**Tasks**

1. `lib/cloudinary.ts` (server-only):
   - Config from `env` (`CLOUDINARY_CLOUD_NAME/API_KEY/API_SECRET`).
   - `cloudinaryUrl(publicId, transforms)` building
     `https://res.cloudinary.com/<cloud>/image/upload/<transformations>/<publicId>` with
     `f_auto,q_auto` and width/height/format steps.
   - `blurUrl(publicId)` → tiny `w_24,e_blur:300` data URL (or a stored placeholder).
   - `listFolder(folder, opts)` using the Admin API with `next_cursor` pagination (for
     `sync:album`).
   - `resourceByPublicIds(ids[])` → `{ public_id, width, height, format }` (used by upload
     completion, A3).
   - `createArchive(publicIds)` → signed zip URL (for `zip:album`).
   - `signUploadParams({ publicId, folder, maxBytes, formats })` → `{ timestamp, signature }`
     using the documented parameter sorting + SHA-1, never logging the secret.
2. `components/ui/CloudImage.tsx`: `next/image` with `unoptimized` **off** — instead use a
   `loader` that points at `cloudinaryUrl` so `srcset` sizes are generated by Next; explicit
   `width`/`height` from the `Photo` row; `placeholder="blur"` when `blurDataURL` exists;
   `sizes` prop required; `alt` required (falls back to caption, then to `""` only for
   decorative).
3. Unit-test URL construction (transform ordering, special characters in `publicId`).

**Acceptance criteria**

- [ ] No API secret is importable from a client bundle (grep the built chunks for the secret —
      add a CI step `! grep -r "CLOUDINARY_API_SECRET" .next`).
- [ ] Images render with explicit dimensions (CLS 0 on the gallery route).
- [ ] `listFolder` handles > 100 assets via cursor (test with a mocked paginated response).

**Tests:** unit (`cloudinary-url.test.ts`, `sign-params.test.ts` — assert signature matches a
known vector), integration (paginated list with mocked fetch).

**Exit gate:** `pnpm test:unit` green; the client-bundle secret grep added to CI.

## Subphase 3.3 — Album scripts: `sync:album` and `zip:album`

**Goal:** the pro workflow from §11.2 with no bulk-upload UI.

**Files:** `scripts/sync-album.ts`, `scripts/zip-album.ts`, package.json scripts.

**Tasks**

1. `pnpm sync:album <slug>`:
   - Reads `Album` by slug (404 with a list of valid slugs).
   - Lists the Cloudinary folder `wedding/<slug>` (paginated), skipping non-image resources.
   - Upserts `Photo` by `publicId`: width, height, `source = ADMIN`, `status = APPROVED`,
     `albumId`; ordering derived from the filename (natural sort, so `2.jpg` < `10.jpg`).
   - New assets get `sortOrder` appended after existing ones; existing assets keep their order
     unless `--reorder` is passed (then recompute by filename).
   - Prints a summary: created, updated, unchanged, skipped.
   - `--dry-run` flag prints the plan without writing.
   - Never deletes rows for assets that disappeared from Cloudinary — print a warning instead
     (deletion is an explicit `--prune` with a confirmation prompt).
2. `pnpm zip:album <slug>`:
   - Builds an archive of approved photos in that album, prints the signed URL and writes it to
     `RUNBOOK`-documented location; expires within 24 h.
3. Both scripts use `tsx`, validate env through `lib/env.ts`, and refuse to run when
   `DATABASE_URL` is missing (clear message).

**Acceptance criteria**

- [ ] `pnpm sync:album pre-wedding --dry-run` lists exactly the assets in the folder.
- [ ] Running it twice creates no duplicate rows (idempotent upsert by `publicId`).
- [ ] Natural sort ordering verified with a fixture containing `1, 2, 10` images.
- [ ] `zip:album` returns a URL that downloads a valid zip (verify by downloading once).

**Tests:** integration for the upsert/sort logic with a mocked `listFolder`; unit for the natural
sort comparator.

**Exit gate:** both scripts run successfully against the real Cloudinary folder (output pasted).

## Subphase 3.4 — Guest uploads: sign, upload, complete (F7)

**Goal:** a QR-scanned upload that works on a bad venue connection, with HEIC handled and
impossible-to-fake rows (A3).

**Files:** `app/upload/[token]/page.tsx`, `components/ui/UploadDropzone.tsx`,
`app/api/upload/sign/route.ts`, `app/api/upload/complete/route.ts`,
`lib/validation/upload.ts`.

**Contracts**

```
POST /api/upload/sign      Auth: x-upload-token header (or body.token)
  Body: {}  (one file per call)
  200 → { ok, data: { uploadUrl, publicId, folder, apiKey, timestamp, signature,
                     maxBytes, allowedFormats } }
  401 INVALID_TOKEN · 403 UPLOADS_CLOSED · 400 VALIDATION
POST /api/upload/complete  Auth: x-upload-token
  Body: { publicId: string, caption?: string }
  200 → { ok, data: { photoId } }        (idempotent: existing row returned)
  401 INVALID_TOKEN · 403 UPLOADS_CLOSED · 404 ASSET_NOT_FOUND · 400 VALIDATION
```

**Rules**

- Window: `settings.uploadsOpen === true` **and** (`uploadsCloseAt` null or `now < uploadsCloseAt`).
- Token: constant-time compare against `Setting.uploadToken`; missing/null token ⇒ 401 always
  (never a 500).
- `publicId` is generated **server-side** at sign time:
  `wedding/guest-uploads/<yyyy>/<mm>/<random 16 hex>` and returned to the client, so `complete`
  knows exactly which asset to verify.
- Signature covers `folder`, `public_id`, `timestamp`, `max_file_size`, `allowed_formats`.
- `complete` calls `resourceByPublicIds([publicId])`; a miss ⇒ 404 `ASSET_NOT_FOUND` and **no**
  row is created. Width/height come from Cloudinary, not from the client (A3).
- Row: `album = guest-moments`, `status = PENDING`, `source = GUEST`,
  `uploadedBy = guestCode ?? "guest"` (cookie present ⇒ attribution), `altText = caption`,
  `sortOrder = 0`.
- Repeat `complete` for the same `publicId` ⇒ 200 with the existing `photoId` (client retry safe).

**Tasks**

1. Both routes as specified, with Zod validation and the standard envelope.
2. `/upload/[token]` page (`force-dynamic`):
   - Validates token + window server-side before rendering; invalid/closed ⇒ a branded
     "this upload link is not active" page with the couple's names and RSVP contacts — never a
     stack trace or a hint about the token.
   - Short privacy notice (what is collected, that it is moderated, how to request removal) linking
     to `/privacy`.
   - Dropzone: multi-file, images only (`accept="image/*"`), per-file progress, cancel, retry,
     max 10 files per session, client-side compression for JPEG/PNG over 2 MB using
     `browser-image-compression` (max 4000 px long side, quality 0.82), **HEIC passed through
     untouched** (Cloudinary converts on delivery with `f_auto`).
   - Per file: `sign` → upload to `uploadUrl` (FormData with the signed fields) → on 200,
     `complete` → mark file done. On failure: clear error, retry button, and a "tell us at the
     table" note with the couple's contact.
   - Network handling: sequential uploads (not parallel) to survive a congested venue; each file
     independent so one failure doesn't kill the batch.
3. Progress announced via `aria-live="polite"`; dropzone keyboard accessible (a real `<input
type="file">` behind the styled label).

**Acceptance criteria**

- [ ] Wrong/absent token ⇒ 401 envelope; expired window ⇒ 403; both also produce the friendly
      page.
- [ ] Calling `complete` with a `publicId` that was never uploaded ⇒ 404 and no `Photo` row
      (test with a random id).
- [ ] A real upload from an iPhone produces a visible, moderated `PENDING` row with correct
      width/height (device test at the exit gate).
- [ ] Killing the network mid-upload leaves a retryable state, not a silent failure.
- [ ] Rate limiting is absent by design now (Sprint 4) but the route is already shaped for it —
      a single helper call site is stubbed and documented.

**Tests**

- Integration: `sign` happy path + bad token + closed window; `complete` verification path with
  mocked `resourceByPublicIds` (found → row created; not found → 404 no row; existing → idempotent).
- E2E `upload.spec.ts`: against mocked Cloudinary in CI — open `/upload/<token>` with the window
  open, choose a file (Playwright `setInputFiles`), assert a `PENDING` row appears with
  `source = GUEST`. Real-Cloudinary variant tagged `@cloudinary`, skipped in CI.

**Exit gate:** integration + e2e green; iPhone HEIC upload demonstrated and screenshotted.

## Subphase 3.6 — Admin settings, mode toggle and QR (F14)

**Goal:** one switch changes the whole site, in seconds, from a phone.

**Files:** `app/admin/settings/page.tsx`, `app/api/admin/settings/route.ts`,
`components/admin/ModeToggle.tsx`, `components/admin/UploadWindowPanel.tsx`.

**Contracts**

```
GET  /api/admin/settings            → { ok, data: Settings & { uploadQrUrl } }
PATCH /api/admin/settings           Body: Partial<{ mode, rsvpDeadline, uploadsOpen, uploadsCloseAt, liveStreamUrl }>
                                    → { ok, data: settings }
POST /api/admin/settings/upload-token   → { ok, data: { token, qrSvg } }   (rotates)
```

**Tasks**

1. Mode toggle: three-way `PRE | LIVE | POST` segmented control with a confirmation modal
   explaining exactly what changes (RSVP open/closed, albums, uploads, hero copy). On success:
   `revalidateSite([...])` **and** a toast confirming "Site updated — may take a few seconds".
2. RSVP deadline editor (date picker, WAT semantics — store as UTC midnight-plus-time explicitly;
   document that the deadline is end-of-day `Africa/Lagos`).
3. Upload window: `uploadsOpen` switch, `uploadsCloseAt` datetime, **regenerate token** button
   (confirmation modal: "any QR code already printed will stop working"), QR rendered from the
   returned SVG via `qrcode.react` pointing at
   `NEXT_PUBLIC_SITE_URL + "/upload/" + token`, plus "Copy link" and "Print" (`window.print()` with
   a print stylesheet that prints only the QR and the URL).
4. Live-stream URL field (validated `https`), saved and used by the LIVE-mode banner.
5. Every PATCH writes `AuditLog` (`settings`, key changed, old → new — redacted for the token).

**Acceptance criteria**

- [ ] Toggling `PRE → POST` changes the public gallery lock state within ~5 s (test asserts the
      cached read returns the new mode after `revalidateSite`).
- [ ] Regenerating the token invalidates the old one (old `/upload/old` now shows the inactive
      page).
- [ ] QR scans to the correct URL (verify by decoding the generated SVG/PNG in a test or manually).
- [ ] Deadline is interpreted in WAT: a test at `2026-12-05T22:59Z` is open, `2026-12-06T00:01Z`
      (01:01 WAT on the 6th) is closed — match the documented rule exactly.

**Tests:** integration (settings PATCH, token rotation invalidation, revalidation),
unit (deadline boundary helper), e2e `mode-toggle.spec.ts` (admin flips mode → public page
reflects it).

**Exit gate:** `pnpm test:e2e` green including the mode-toggle spec.
